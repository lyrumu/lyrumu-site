# Notes to Hugo

把用户点名的 Notes 笔记迁移到本站。迁移价值在于把 Obsidian 原稿编排成适合网页浏览、目录导航和快速扫描的文章，同时保留原意和信息，并配齐对应的文章卡片图片。不提交、不推送、不部署。

## 核心原则：内容忠实，呈现重构

- 默认保留原文的具体措辞、观点、信息、例子、命令、提示词及叙述顺序。不要仅因原文简短、口语化或像笔记，就进行润色、概括、扩写、删减或重组论述。
- 排版优化不是把 Wiki 图片链接换成 Markdown 后原样复制。必须根据内容关系重新选择标题、段落、表格、列表、步骤、代码块、提示词块、引用和图片说明，让目录有用、重点可扫读、操作可复制、图片能对应上下文。
- 允许移动句子到所属标题、列表项、表格单元格、图片标题或步骤中；这是呈现重构，不是内容改写。不得改变原意、遗漏信息或为了版式添加新的观点。
- 只有明显错误或确有必要时才局部增删改，例如明确的错字、误粘贴重复、语法转换导致的歧义、无法理解的内部指代、必要的来源归属或会误导操作的前提缺失。改动限于解决问题所需的最小范围；不能以“更正式”“更完整”“访客可能需要”为由补写教程、例子、建议或总结。
- 不确定某处是否错误、是否需要删改时，默认保留并在交付时指出；会影响理解或使用且无法保守处理的，先询问。任何非排版的内容增删改都应有具体理由，并在最终回复中说明。

## 固定边界

- 项目根目录是 `/Users/lyrumu/project/lyrumu-s-page/knowledge-base`；源仓库是 `/Users/lyrumu/project/Notes`。
- Notes 全目录只读：不得编辑、删除、移动或重命名任何源文件、附件及 `.obsidian` 配置。
- 写入范围限于目标文章包 `content/notes/<name>/`、对应卡片图片 `assets/image/notes/`、`data/notes.yaml` 中对应文章的映射；不改布局、样式、其他数据项或其他文章。文章迁移、正文排版/内容修改、配图及其映射不写入 `DONE.md`；`DONE_ARCHIVE.md` 是只读历史备份，也不得修改。
- 不执行 `git add`、commit、push 或部署，也不启动 Hugo server。
- 用户未明确点名源文件，或名称匹配多个文件时，先询问准确路径。
- 目标目录已存在但无法确认是同一篇文章时，不覆盖，先询问。

## 先理解当前项目

每次执行都以现场文件为准：

1. 查看 `git status --short` 和目标相关 diff，保护用户未提交改动。
2. 完整读取 `archetypes/notes.md`；它是新文章 front matter 字段、顺序和默认值的唯一模板。
3. 浏览 `content/notes/*/index.md` 的 front matter 与标题结构，再完整读取 2–4 篇与源稿在主题、篇幅或类型上最接近的文章。
4. 读取 `content/notes/_index.md` 中会级联到文章的配置。不要把旧文章遗留的额外字段反写进 archetype。

从现有文章学习标题层级、分隔符、提示块、代码块、图片写法和 taxonomy 词汇；保留源稿的语气与信息密度，不为匹配其他文章而重写内容。

## 网站化编排标准

完整读完原稿后，先按内容关系规划层级和块类型，再写目标文件。逐块使用最合适的 Markdown 表达：

- **层级**：正文不重复页面标题；`##` 表示主要章节，`###` 表示并列方法或阶段，`####` 只用于确有下一级的内容。标题应让自动目录能够概括全文，避免把“关键要素”“步骤”等孤立标题重复塞进目录。
- **并列信息**：至少包含两个稳定字段的短内容优先用表格，例如“要素／作用”“命令／用途”；长段落和图片不塞进表格。
- **流程**：有先后关系的内容用有序列表；无顺序的并列项用无序列表。不要用散落段落模拟步骤，也不要给无顺序内容强加序号。
- **命令与提示词**：终端命令使用带语言标记的围栏代码块；可直接复制的自然语言 prompt 使用 `text` 围栏代码块，不用斜体引用块或行内代码承载长文本。简短术语、按键和参数才使用行内代码。
- **提示与前提**：版本范围、必要前提、注意事项或推荐项用引用块，并紧邻相关内容；普通正文和 prompt 不滥用引用块。
- **图片**：图片放在其说明或步骤之后，使用准确替代文本；需要读者识别阶段或差异时增加 Markdown 图片标题，使渲染结果出现图注。连续图片必须逐张说明，不能形成无标签的截图长墙。
- **阅读节奏**：一个段落表达一个要点；保留必要强调，但避免整句加粗和重复强调。正文分隔符统一使用单独一行 `***`，只用于主要章节转换，不在每个小节之间反复使用；`---` 只用于 front matter 边界。

按文章类型采用最小但清晰的骨架：

- **配置／命令笔记**：每项任务用 `##`；任务内按“执行／恢复”或真实阶段使用 `###`；前提紧邻命令；每个命令可独立复制；恢复方式不能埋在段尾。
- **课程／方法长文**：课程章节用 `##`，并列方法用 `###`；关键要素优先表格化，流程改为有序步骤，prompt 使用 `text` 代码块，过程截图按阶段配图注。长文目录应能直接定位方法，正文不连续堆叠同级碎片。

完成稿若除 front matter、链接和空行外仍基本等同 Obsidian 原文，视为迁移未完成；应重新检查是否遗漏了可改进的信息层级、块类型、可复制性、图注和扫描节奏。

## 整理规则

### 目标与模板

- 用户指定目标目录名时照做；否则用源文件名去掉 `.md` 作为目录名，仅把连续空格改为 `-`。保留 Unicode，不擅自翻译 URL。
- 新文章先运行 `hugo new content "notes/<name>/index.md" --kind notes`，确保实际使用 `archetypes/notes.md`，再填写内容。
- 不使用 `--force`。更新既有文章时先读完现有页面，保留站点侧的人工修改并做合并，不整篇覆盖。
- `slug` 默认留空；`weight` 默认 `0`，除非用户明确要求置顶。
- 新文章 `date` 使用整理当天日期；更新已有文章保留原 `date`，有实质更新时启用 `showDateUpdated` 并填写当天日期。
- `title`、`description`、tags 和 categories 必须来自文章真实内容，并优先复用站内已有 taxonomy。description 用文章主要语言写成一条具体摘要，不写空泛宣传语。

### 正文

- 保留原文内容和作者的真实声音，包括个人经历、第一人称、简洁表达及有意强调；不把助手的整理行为写成作者经历。只修正明确的错字、误粘贴重复、残缺层级和 Markdown 格式。
- 把 Obsidian Wiki 链接、嵌入、callout、脚注或专用语法改成本站可渲染的标准 Markdown。不能发布的内部链接改为自然文本；若它对理解不可缺少，先询问用户。
- 仅在脱离 Obsidian 后确实无法理解或容易误用时，补足最少的指代、前提或来源说明；默认不新增开场、步骤、风险段落或结尾，不虚构经历、数据或结论。
- 不为了“像正式文章”而扩写无信息量的段落，也不抹平用户原本简洁、个人化的语气。

### 读者视角（发布前必查）

- 正文面向首次到访的网站读者，不面向委托迁移的用户。视角检查遵守“排版为主，内容少动”：只修正必要的指代和助手加入的编辑口吻，不因此重写整段或补充原文没有的内容。
- 不把交付汇报、编辑过程和向作者交代的待办写入正文，例如“原笔记记下了”“本次整理未验证”“你提供的材料”“按你的要求”。这类内容仅在最终回复中说明，不写入 `DONE.md` 或另建文章变更日志。将“原笔记中的命令对照图”改成“下方命令对照图”，将“笔记中记下的做法是……”改成具体方法及适用情境。
- 保留访客需要的来源署名、版本范围和真实的不确定性；不用面向作者的免责声明代替。不能通过删掉“未验证”就把未知事实写成确定结论，也不能虚构体验。原文已有但尚未核实的模型名等内容不因未核实而擅自删除或替换，疑点在交付时指出；助手加入的编辑待办移出正文。用户明确要求保留的来源链接占位仍保留。
- 通读标题、摘要、开场、正文、图片说明和结尾，逐句判断“这是在向访客讲内容，还是在向作者报告整理工作”。改掉后者；不要机械地把所有“我”改成“你”，真实个人叙述可以保留。

### 网页剪藏或 AI 原始材料

- 根据正文、front matter、来源链接和用户提示判断材料属性；不确定是否为转载时先问，不把第三方内容冒充用户原创。
- 网页剪藏可删除导航、广告、推荐阅读、重复页脚等页面噪音；不把作者正文当作噪音。确因版权边界需要摘要或改写时，限于必要范围并说明原因，不把这项例外套用于用户自己的笔记。
- 保留清晰的原始来源链接和必要署名；短引文明确标注，观点与原作者区分。
- 命令、安全建议、价格、版本、平台规则或其他易变事实不能盲目照抄。用户要求更新或核实时，查当前的一手资料；否则保留原稿时间语境，并对无法确认的内容明确标注或在发布前询问。

### 图片与附件

- 只处理正文实际引用的本地附件。先解析相对路径及 Notes 根目录下的 `assets/`，再复制到目标文章包的 `image/`；Notes 中原件保持不动。
- 将 `![[assets/example.png]]` 等 Obsidian 嵌入改为 `![准确替代文本](image/example.png)`。文件名冲突时先采用可读、稳定的新名字并同步链接。
- 不复制未引用附件和 `.obsidian` 内容。远程图片不自动下载；若它是文章必要内容且用户没说明保留、替换或删除，先询问。

### 文章卡片配图（默认必做）

- 新迁移的每篇文章都生成一张主题相关的卡片图；更新既有文章时，保留已有合适配图，缺图才补，用户要求更换时再重新生成。用户明确不需要配图时遵从。
- 先读 `layouts/partials/article-link/card.html`、`assets/css/_13_notes-card.css` 和 `data/notes.yaml`，实际查看 2–3 张现有 `assets/image/notes/` 配图。按当前站内图片学习风格，不只凭文字印象生成。
- 当前基调是暖米白纸纹、纸雕或剪纸拼贴、低饱和炭灰/灰蓝/橄榄色与少量陶土色、柔和自然光和浅阴影。以文章的核心对象构图，保持同批图片的材质、色调、光线和细节密度一致；不直接复用课程截图当生成封面，不加入无依据的品牌标志或大段文字。
- 使用 `imagegen` 技能与内置图像生成工具，每篇单独生成。优先约 16:9 横图；主要对象留在中央安全区域，上方元信息和底部标题面板需要留白，并考虑 `object-fit: cover` 裁切。生成后实际查看图片，确认主题、风格、裁切余量和无乱码。
- 将最终图片复制到 `assets/image/notes/<name>.<ext>`，在 `data/notes.yaml` 的 `items` 中按当前模板使用的文章标识（当前为 `.File.ContentBaseName`）添加或更新唯一对应项，`image` 使用 `image/notes/<name>.<ext>`。复用 Hugo 的 WebP 缩放和模糊占位管线；不要仅把文件放进目录而不接入卡片，也不要为卡片图额外开启文章正文的 hero。
- 保护已有图片与映射；更换配图采用新文件名，不删除旧图。生成工具不可用时，完成其他整理并明确报告配图未完成，不以图标或占位图冒充完成。

## 完成检查

1. 比较源 Markdown 整理前后的 SHA-256，确认 Notes 原件未变；有本地源附件时同样确认未变。
2. 逐段对照源稿与目标文章，检查是否遗漏或擅自新增、改写具体内容；逐项确认非排版改动的必要性。再按“层级、表格／列表、步骤、命令／prompt、图片图注、强调、分隔符、读者视角”逐项审查，确认文章已完成网站化编排，而非仅做语法转换；检查没有残留 `![[...]]`、`file://`、本机绝对路径、抓取页面噪音或失效的内部链接。
3. 核对每篇卡片图已落盘、映射唯一且路径可解析，缩放与占位沿用现有管线；运行 `git diff --check`。
4. 运行一次非服务构建：`hugo --renderToMemory --themesDir themes --theme blowfish --config hugo.toml --cacheDir /tmp/lyrumu-hugo-cache`。若用户已有可访问的本地预览，复用它检查桌面端和窄屏的标题、表格、代码、图注与连续图片节奏；不自行启动长期服务。没有可用预览时，只把构建通过称为构建验证，并明确浏览器视觉验收待用户完成。
5. 最终回复简要报告目标文件、复制的附件、生成的卡片图及其风格、必要的非排版改动理由、源文件未变证明、验证结果，以及仍需用户决定的事项。明确说明未做 Git 发布；不为这些内容更新 `DONE.md` 或另建日志。
